## 0. 现状实测（不是估计，全部当场跑出来）

| 维度 | 实测值 | 含义 |
|---|---|---|
| 代码规模 | 256 个 `.py`，**99,375 行** | 单人可维护上限附近，无模块化 |

## 1. P0 级建议（不做就等于产品不可用）

### P0-1　页面体积从 9.04 MB 降到 < 1.5 MB（最大可用性问题）

**根因实测**：2,084 只个股，每只一个 4,053 字符的 `<tr>`，合计 7.95 MB = 页面 88%。其中：

| 冗余项 | 占用 | 可压缩手段 |
|---|---|---|
| `.s-scores` 单元格 | 1,057 字符/行 = **2.15 MB** | 改 CSS class + `data-v` 属性（5 档配色只有 5 个 class） |
| 43 个 `data-*` 属性 | 1,329 字符/行 = **2.71 MB** | 合并为单个 `data-j` JSON 属性 / 或移入 `<script>` 数据岛 |
| 40,423 次内联 style（384 种） | 估 **1.8 MB** | 全部提为 `<style>` 里的 class |
| `data-*-text` 四件套 | 0.64 MB（8.1%） | 保留（详情区需要） |

**具体改法（三步，风险递增）**：

**Step 1（零风险，先做）**：内联 style → CSS class
```python
# 现状（40,423 次，384 种）
'<div class="s-score" style="background:#22c55e" title="...">8.3</div>'
# 改为
'<div class="s-score sc-4" title="...">8.3</div>'
# <style> 里加：.sc-0{background:#ef4444}...sc-4{background:#22c55e}
```
预计省 **1.8 MB**，纯机械替换，不动任何语义。

**Step 2（中风险）**：`.s-scores` 的 9 个 div 改为紧凑编码
```python
# 现状：9 个 div × ~117 字符 = 1,057 字符
# 改为：<td class="s-scores col-scores" data-sc="8.3,9.0,9.5,8.7,8.0,8.0,5.6,..." data-nf="2">
#       + 一小段 JS 在 onload 时展开（或用 CSS ::before 无法做到，必须 JS）
```
预计省 **2.0 MB**。代价：`<td>` 内容依赖 JS。**必须保留 `data-sc` 原文供无 JS 环境降级为纯文本。**

**Step 3（结构性，收益最大）**：默认只渲染前 200 只，其余按需加载
```python
# 2,084 只里，实际有人看的不会超过前 100 名。
# 方案：默认输出 top-200 完整行；其余 1,884 只压缩为 data-island
#   <script type="application/json" id="rest-rows">[{...}, ...]</script>
#   用户点「加载全部」或筛选时才渲染。
```
预计页面降到 **1.2~1.5 MB**（含全部数据，只是延迟渲染）。

**⚠️ 必须同时做的一件事**：确认部署端开启 gzip/brotli。实测 9.04 MB → 0.92 MB（90%）。如果现在是裸传，**先开压缩，一行配置顶上面三步**。这是最高 ROI 的单点改动。

**验收标准**：
- 首页 HTML ≤ 1.5 MB（未压缩）
- 移动端 Chrome 首屏可交互 < 3s（用 Lighthouse 实测）
- 全部 2,084 只数据不丢失（延迟渲染不算丢）
- 页面自测 `audit_round112_page_selftest.py` 69 项仍全过

### P0-2　K 线库从 341 日扩到 ≥1500 日（今天已实测可行）

**这不是"建议"，是已验证可执行**。刚实测：

| 测试 | 结果 |
|---|---|
| 新浪 `datalen=2000` | ✅ 返回 **2,000 根，回溯到 2018-08-01** |
| 单只 1500 根耗时 | 0.37~0.60s（均值 **0.48s**） |
| 2,138 只串行 | **≈ 17 分钟** |
| 8 并发 | **≈ 2 分钟** |
| 产物体积 | 单只 ≈154KB → 全池 **≈138 MB**（现 33MB） |
| 覆盖的行情段 | 2018 熊 / 2019-21 牛 / 2022 熊 / 2024 反弹 / 2025-26 → **跨 2 轮完整牛熊** |

**为什么这是 P0 而不是 P2**：今天所有「因子有效/无效」结论都写在单一样本期上。`audit_round113b` 已经证明——**H=20 有 5 个因子"通过"，扩样本证伪后全部淘汰**。也就是说：**没有长样本，我们连自己是对是错都不知道**。

**实施要点**：
1. 新写 `backfill_klines_history.py`（不要改 `append_klines_sina_fallback.py`，日更链路不能动）
2. 关键设计：**只补 `date < 库内最早日期` 的部分，已有日期一律不覆盖**（前复权平移风险，与现有脚本同一原则）
3. 输出到 `data/klines_long_ext.json`（新文件，不动原库）→ 交叉验证一致后再合并
4. 必须做一致性校验：重叠期（2025-06-09 ~ 2026-11-02）两库收盘价必须**逐日完全相等**，不等则拒绝合并
5. **接入日更链路**（项目铁律：一次性脚本不在日链=必然陈旧）

**验收标准**：
- `klines_long_ext.json` 覆盖 ≥1,500 个交易日
- 重叠期 341 日收盘价 100% 一致（差异 > 1e-6 即 FAILED）
- 日更链路新增 `append` 步骤仍只动最新 N 日

### P0-3　「因子有效性」必须按持有周期分区展示（口径错配）

**实测证据**（`recommendation_track.json`，12 推荐日）：

| 分组 | T+1 超额 | 胜率 |
|---|---|---|
| Top10%（total ≥ 85.3） | **−1.28%** | 41.0% |
| Bot10%（total ≤ 66.5） | −0.76% | 41.0% |
| Spearman(total, T+1 超额) | **−0.0257** | — |

**排名越高反而越差**。80 分以上的股票次日跑输低分股——用户看到「85 分」去买，第二天亏钱，这是**体验毁灭级**的问题。

**根因不是模型错，是维度频率错配**：9 个生效维里，fund/growth 是季度频率、quality 是年报频率、size_growth 是市值结构。**没有一维是设计来预测次日方向的**。

**改法**：页面按持有周期分档，每档只显示该周期有效的维：
```yaml
月度以上: 全部 9 维（total 全维参与）
周级 H=5: tech_neg / bias60 / rsi_rev / ep
日级 H=1: 不给 total 排序，只给「事件/流动性提示」
```
并在 total 数字旁加一行强制说明：**「本分数为月度选股口径，不适用次日交易」**。

**验收标准**：页面无任何位置把 total 与「次日」并列；自测新增断言防回归。

## 2. P1 级建议（不做会持续踩坑）

### P1-1　`daily_pipeline.yaml` 契约化（已踩 2 次静默缺失）

现状：256 个脚本、日更顺序靠 `.workbuddy/memory` 里的**文字**约定。已发生的事故：
- `fetch_focus_list` 在 gen_report 之后跑 → 焦点池空
- `fetch_bench → regime_model` 在 gen_report 之后跑 → 整块静默跳过

**改法**：
```yaml
stages:
  - name: fetch_bench
    cmd: python fetch_bench.py
    outputs: [data/bench/000985.json]
    requires_date: "{{ trade_date }}"     # 输出必须含目标交易日
  - name: regime_model
    cmd: python regime_model.py
    requires: [fetch_bench]
    outputs: [regime_forecast.json]
```
跑完逐个校验 `outputs` 的**日期戳 == 目标交易日**，任一不符 → **exit 2 硬失败**（不是告警）。

对应方法论第⑭条：*同一数据文件被两处读取，必有一处忘校验 → 故障注入是唯一发现手段*。

### P1-2　`signal_health.json` 衰减监控（今天手工发现，应自动报警）

实测一个正在失效的信号（`audit_round114f.V5`）：

| 区间 | 均值 | 胜率 |
|---|---|---|
| 2025H2 | +4.50% | 79.7% |
| 2026H1 | +3.49% | 65.3% |
| **2026H2** | **+2.22%** | **48.9%** |

**单调衰减到 48.9%（已低于随机）**，但项目里**没有任何机制会发现这件事**。

**改法**：每个上线信号/因子跑一条滚动序列（60 日 IC + 胜率）→ `signal_health.json`；跌破阈值（如胜率 <52% 连续 20 日）→ 页面顶部黄条。可复用现有 `regime_forecast` 的日期门禁机制。

### P1-3　评级双口径必须 tooltip 教育（我自己都误判过）

- `scored.rating` = 绝对阈值（A:419/B:1027/C:620/D:18）
- 页面 = 当日截面分位（S 前 5% = 104 只、A 5%~15% = 209 只）

写页面自测时我**先把「五级只数之和 ≠ 样本数（313 vs 2084）」误判成失败**——说明这个双口径是误解高发点。页面 B/C/D 印的是**累计百分位阈值**（`前50%`/`前88%`/`后12%`）而非只数，这是设计。

**改法**：徽标加 tooltip「本档 = 当日分位，非绝对分」；图例处直接算只数给人看（「S = 今日前 5%（104 只）」）。

### P1-4　根目录 199 个 json / 54 MB 无归档（可维护性）

`audit_round*.json` 从 round10 累积到现在，全部平铺根目录。新人无法判断哪个是现行口径。

**改法**：`reports/archive/` 按 round 归档，根目录只保留「现行口径」的 ≤20 个文件；加 `MANIFEST.md` 标明每个文件的状态（现行/作废/仅证据）。

## 4. 建议执行顺序与验收

| 顺序 | 事项 | 收益 | 验收 |

| 1 | **部署端开 gzip/brotli** | 9.04→0.92MB，一行配置 | `curl -H "Accept-Encoding: gzip" -I` 见 `Content-Encoding` |

| 5 | `.s-scores` 紧凑编码（P0-1 Step2） | −2.0MB | 无 JS 时降级为纯文本 |
| 6 | 默认渲染 top-200（P0-1 Step3） | 1.2~1.5MB | 2084 只数据不丢 |
| 7 | `daily_pipeline.yaml`（P1-1） | 消灭静默缺失 | 故障注入测试通过 |

| 10 | json 归档（P1-4） | 可维护性 | 根目录 ≤20 个 |

**做 1~4 项即可解决 80% 问题**：页面能打开（0.92MB）、结论敢信（1500 日）、口径不错配。

## 5. 一句话总结

这个项目**分析深度已经过剩，可用性严重不足**：

- 9.04 MB 单页 = 移动端打不开，而 88% 体积是 2,084 行 × 4,053 字符的个股行，其中光是**重复内联样式就有 40,423 次（仅 384 种唯一值）**
- 341 日样本 = 所有「有效/无效」都在一期行情上，而**扩到 1500 日只需 17 分钟**（已实测）
- 「85 分买次日亏 1.28%」= 口径错配，不是模型错

**最该先做的一件事**：先确认部署端有没有开 gzip。如果有，9.04MB 实际传输 0.92MB，那 P0-1 的紧迫性下降一半；如果没有，这是一行配置解决 90% 体积问题——比改代码划算得多。
