> 方法：全部结论均由实证核查得出（代码实现 + 数据分布 + 唯一内核重算），未使用推测。

## 严重程度定义

| 级别 | 含义 | 处置要求 |
|---|---|---|
| **P0** | 影响评分正确性或数据可靠性，可能导致结论错误 | 立即修复，修复前不得对外引用相关结论 |
| **P1** | 影响模型有效性或运行可靠性，不直接算错但埋雷 | 下一轮迭代修复 |
| **P2** | 口径/文档/工程卫生问题，影响可维护性与可复核性 | 择机修复 |
| **P3** | 优化项 | 有余力时处理 |

## 影响范围定义

- **全池**：影响 1798 只全部
- **大盘**：影响 >100 只
- **头部**：影响前 50
- **局部**：影响 <20 只

# 一、P0 级（6 项）

## P0-1 quality 维不约束 ROE 极端值，低 ROE 公司拿满分

**类型**：评分口径缺陷
**影响范围**：全池；头部 11/50（ROE<10 但 quality≥8.5）

### 实证

quality = 质量族（资本回报/现金流盈余质量/稳健风控 三组等权）**池内分位 ×10**，
ROE / OCF/NI / accruals 只作为**扣分项**（`ocf_ni<0` 扣 2.0、`accruals<-10` 扣 1.5），**没有任何绝对下限约束**。

```
ROE<-50   (31只): quality 均值 1.96，范围 0.00 ~ 9.82   ← 最高 9.82
ROE 0~30 (1341只): quality 均值 4.94，范围 0.00 ~ 10.00
ROE>100    (3只): quality 均值 3.49，范围 0.00 ~ 9.82
```

极端案例（同为 9.82 分，天壤之别）：

| 标的 | ROE | quality | flags |
|---|---:|---:|---|
| 紫竹高科 | **+451.09%** | 9.82 | 无 |
| 郑州煤电 | **−65.86%** | 9.82 | 无 |

根因：`fund_split.family_scores` 把子因子**等权平均成原始值**再 rank，
`rank_pct` 直接排序**不做 winsorize** → ROE 极值既不上限也不下限。
同时三组等权平均会把 ROE 的极端值"洗"进其他两组，掩盖信号。

### 修改方案

1. **加绝对下限护栏**（最小改动，优先做）：在 step2 消费点（`step2_stockscorer_v2.py:5546` 附近，
   与现有 `_q_pen` 同处）追加：
   ```python
   _roe = r.get("roe")
   if isinstance(_roe, (int, float)) and _roe < 0:
       s_quality = max(0.0, s_quality - 1.5)
       quality_cash_flags.append("roe<0")
   ```
   扣分力度建议 P0 试 1.5、负 ROE 低于 −30% 再叠加 1.0。
2. **子因子 winsorize**（根治）：在 `fund_split.family_scores` 内对每个子因子先做
   1%~99% 分位截断（`np.clip(v, q01, q99)`）再等权平均，避免单因子主导。
3. **组内权重改为可配**：ROE 组给 0.4、现金流组 0.4、风控组 0.2，
   让 ROE 不至于被平均掉（需同步 `fund_split.Q_GROUPS`）。
4. **留痕**：所有扣分写入 `quality_cash_flags`，页面披露「因 ROE 为负被扣分」的标的数。

> 需老大裁决：扣分力度与是否改组内权重。改组内权重属模型口径变更，
> 按铁律「过程可迁、披露不可迁」需同步八处权重入口 + 页面披露。

## P0-2 权重覆盖守卫靠字段存在性，脆弱且已在 v5 版本下"侥幸生效"

**类型**：数据安全 / 静默失效风险
**影响范围**：全池权重表（一旦失效，评分口径整体漂移）

### 实证

`factor_eval.py --optimize-weights`（日链 Step 3.96 **每天自动调用**）会**整份 dict 覆盖写**
`factor_weights.json`（`factor_eval.py:3136/3175`）。防护判据在 3147-3154 行：

```python
cur_managed = bool(_cur.get("weight_constraints")) or str(cur_ver or "").startswith("v4.")
```

当前版本 `v5.0-audit-revg-es` **不以 "v4." 开头**，仅因恰好存在 `weight_constraints` 字段才被拦下：

```
version= v5.0-audit-revg-es
有 weight_constraints 字段? True
cur_managed = True → 守卫生效
```

**一旦 `weight_constraints` 字段被移除/改名，守卫立即失效** → 日链每天静默把 v5 权重
覆盖成拟合的 v3.6-fund-led 版本，且丢失 dim_max 口径与约束元信息。

### 修改方案

1. **守卫判据改为白名单式**（推荐）：显式维护「受管版本前缀」列表
   `MANAGED_PREFIXES = ("v4.", "v5.")`，比 `startswith("v4.")` 抗改名。
2. **再加一道内容级断言**：若新拟合结果缺 `dim_max` 或 `weights` 合计≠1.0，无论版本名一律拒写。
3. **写前留证**：覆盖前先 `.snap_factor_weights_<ts>.json`（铁律「留证改 .snap_*」）。
4. **日链加一步显式校验**：跑 `verify_weights_round36.py`，非 PASS 即中止后续步骤并告警。

## P0-3 factor_eval 日链单步超时，IC 与权重视图静默陈旧

**类型**：运行可靠性 / 披露失真
**影响范围**：IC 视图（已停 6 天）、长面板 IC（已停 12 天）

### 实证

11-24 日更实测：`factor_eval.py --optimize-weights` 单步 >400s 被 SIGTERM，
记 rc=1 降级继续。`factor_ic.json` mtime 停在 **2026-11-18 17:29**（陈旧 6 天），
`data/ic_long_2020.json` mtime 停在 **2026-11-12**（陈旧 12 天 > 7 天阈值）。

风险点：**IC 陈旧但页面无强披露** —— 报告里 `factor_ic` 相关数字仍在展示，
读者无法一眼看出已陈旧 6 天。

### 修改方案

1. **分片/降级优先于超时**：给 `factor_eval` 加 `--shard` 分片参数（同 `append_klines_latest` 做法），
   或改为「只算截面 IC、不跑优化」两条路径分开。
2. **陈旧度硬门禁**：报告渲染时读 `factor_ic.json` mtime，超过 3 天则**该模块整体降级为占位**
   （不展示旧数字），并显示「IC 视图已陈旧 N 天」。
3. **权重优化改为人工触发**：从日链移除 `--optimize-weights`（它本质是研究动作，不是日更必需），
   改为「日更只算 IC 落盘、不动权重」，权重变更走独立流程 + 门控。

## P0-4 长面板缺失 13 个交易日 + 3 个生效维度无列（门控覆盖仅 60%）

**类型**：验证体系缺口
**影响范围**：全池 IC / 门控结论的有效性

### 实证（`panel_audit.json`，2026-11-24 16:28 生成）

```
panel: data/panel_round124_long.json  末日 2026-10-30（1653 截面 × 2257 只）
· panel 末日比最新评分日 2026-11-24 落后 25 个自然日
· 缺 13 个已有评分的交易日（11-04,11-05,11-09,11-10,11-11,11-12,11-16,11-17,11-18,11-19,11-20,11-23,11-24）
· 3 个生效权重维度在 panel 中无列（合计权重 0.40）：
  score_size_comb(0.20)、score_fund(0.15)、score_es(0.05)
```

即：**当前权重里 40% 的部分从未被历史面板检验过**。`factor_eval` 里的
`factor_parity=False` 代理路径已明确标注「结论只能作代理面板诊断」，
但**代理路径用 `missing_rule="zero"`、生产用 `"structural"`，两把尺子不同**。

### 修改方案

1. **面板回填**（根治，工作量大）：用 `step2` 的日产物把 13 个交易日的 8 维全量回填进 panel，
   回填后 `factor_parity=True`，门控才真正覆盖 100% 权重。
2. **回填前加硬门禁**：`factor_parity=False` 时，`weight_admission_gate` **禁止产出可上线结论**，
   报告与文档一律标注「代理面板口径，40% 权重未检验」。
3. **缺列维显式降权**：代理路径下把无列维的权重从目标函数剔除并重新归一，
   避免「按0计入」被误读为「该维实测为0」。

## P0-5 快照/归档产物与生产结论不同源，报告引用陈旧数据

**类型**：数据一致性
**影响范围**：组合模块（今日已实际发生）

### 实证

11-24 日更中 `gen_portfolio_report.py` 报 `KeyError: 'momentum'`，
组合产物停在 **2026-11-18**。报告层日期守卫正确拦截：

```
⛔ 组合区块按裁决不展示：产物日期 2026-11-18 ≠ 数据日期 2026-11-24
```

**拦截机制有效**（这是好消息），但根因未修：组合报告脚本读 `pf['portfolios']['momentum']`，
而 `pick_portfolio` 产出的 dict 里没有 `momentum` 键 → **每次都会 KeyError**。
组合模块实际上长期处于"选了组合但出不了报告"的状态。

### 修改方案

1. **修 KeyError**：改用 `pf.get('portfolios', {}).get('momentum')` 并在缺失时给出明确告警与占位，
   不让异常中断整个报告生成。
2. **组合产物日期自检**：pick_portfolio 成功后立即校验产物日期 == 数据日期，
   不一致则标红并阻断组合区块（现有守卫已覆盖，补上游自检更早暴露）。
3. **组合报告纳入日链必检项**：在 `pipeline_status` 清单里给 `gen_portfolio_report` 单独记步
   （当前它挂在 `pick_portfolio` 的 if 分支里，失败不单独记账 → 属于"漏记"型隐患）。

## P0-6 AI 评估长期走 fallback，ES 维实际上接近失效

**类型**：外部依赖 + 评分有效性
**影响范围**：ES 维（权重 0.05，全池覆盖仅 3.7%）

### 实证

火山方舟 LLM 订阅已过期：

```
⚠️ LLM 调用失败: Error code: 400 - InvalidSubscription
  Your account (2125177653, 0) lacks a valid AgentPlanEnterprise subscription...
⚠️ 使用 fallback 规则生成 ai_assessment.json
fallback: True
```

覆盖率：`score_es` 全池 **66/1798 = 3.7%**，前 50 中 **37/50 缺维**。
按"缺维按0"口径，**ES 维对 96.3% 的标的贡献 0 分**，其 0.05 权重实际只在 3.7% 覆盖上起作用。

同时暴露一个判定问题：普冉股份 ES「超预期」依据是
"实际 +3875.6% vs 预测中枢 +3612.6%"——**实际与预测同源极端失真**，
此时"超预期"判定不具判别力（模型拿两个失真值比大小）。

### 修改方案

1. **订阅续期**（需老大处理）：火山方舟 AgentPlanEnterprise 续费或改用可用模型源。
2. **ES 覆盖不足时的权重处理**：当前是固定分母按0，等价于给 96.3% 标的**隐式扣 0.5 分**。
   建议改为：**覆盖 <30% 时该维权重归零并把 0.05 按比例分配给其余 7 维**（需老大裁决，
   因为这改变总分口径）。
3. **ES 判定加有效性门槛**：当实际增速与预测中枢**同侧且都 >300%**（或都 <−50%）时，
   判为「无法判定」而非「超预期/低于预期」，按缺维处理。
4. **fallback 状态强披露**：页面对 `fallback=True` 用醒目徽标（当前已有 1 处 `rule-fallback`，
   建议升级为首页横幅 + 数字后缀），并披露 ES 实际覆盖率。

3. **修正后增速仍 >300% 的标的名次限制**：在报告层标注「基数效应主导，名次不可直接采信」。

## P1-2 ES 缺维造成双向失真

**类型**：评分口径
**影响范围**：头部 37/50、全池 1732 只

**实证**：有 ES 组均分 **77.17**，无 ES 组均分 **73.88**，差 **+3.28 分**。
高基本面公司（中际旭创 ROE43.8%、协创数据 ROE30%）因 ES 缺维被系统性压低。

1. ES 覆盖 <30% 时该维权重归零（见 P0-6 第 2 条）。

   这与老大"缺维不能算中性"的要求冲突，故**只能在 ES 覆盖不足时临时启用**，
   并明确标注为临时口径。

## P1-7 定时任务仍用后台跑整链，每天都会中断

**类型**：运行可靠性
**影响范围**：日更链路（每日）

**实证**：11-24 的 15:30 定时任务在 `append_klines_latest` 处中断
（日志停 15:43、pgrep 无进程、TSV 只记 3 步）。人工接手补跑 20 步才完成。

根因：`run_daily_local.sh` 包含多个分钟级步骤，单链总时长 30~45 分钟，
automation 会话中断即全链中断。已给 `append_klines_latest` 加了 `--start/--end` 分片，
但**其余长步骤未分片**（factor_eval 同样超时）。

**修改方案**：
1. **分片化长步骤**：factor_eval / archive_fund_universe / verify_qfq_anchor 全部加分片参数。
2. **定时任务改"分批前台 + 可重入"**：每批单独跑并逐条 `--record`，
   中断后从 TSV 最后一个成功步续跑（幂等守卫已支持）。
3. **加 watchdog**：超时未完成则告警并自动分批续跑，而不是静默停在半路。
4. **或改为云端 dispatch 为主**（Actions 已有 workflow），本地仅做核验——
